# Implementation Plan: Input Logging

**Branch**: `001-input-logging` | **Date**: 2026-08-16 | **Spec**: [spec.md](./spec.md)

**Note**: This template is filled in by the `/speckit-plan` command; its definition describes the execution workflow.

## Summary

Build the write-read-delete spine for logging against a user's existing
inputs: `POST /inputs/{id}/logs` creates a uniquely-identified log entry,
`GET /inputs/{id}/logs?range=` reads that input's history back over a
relative date window, and `DELETE /inputs/{id}/logs/{log_id}` hard-deletes a
single entry — all scoped to the current user via a stubbed
`get_current_user` identity seam that returns the same shape the real
Google-OAuth verifier will later return. Built on FastAPI + SQLAlchemy ORM
(schemas kept separate from ORM models) + Alembic migrations against
Postgres in Docker, with OpenAPI auto-emitted to `packages/api-contract`.

## Technical Context

**Language/Version**: Python 3.11+

**Primary Dependencies**: FastAPI (ASGI web framework), Uvicorn (ASGI
server), SQLAlchemy (plain ORM — no SQLModel), Pydantic v2 (request/response
schemas, kept distinct from ORM models), Alembic (migrations), psycopg
(Postgres driver)

**Storage**: PostgreSQL, run in Docker via the backend's `docker-compose.yml`
(no Homebrew, no SQLite fallback). Tables in scope for this feature: `users`,
`inputs`, `input_logs`, plus `captures` created as a stub table (present for
Constitution Principle II, not exercised by this feature's endpoints).

**Testing**: pytest, with FastAPI's `TestClient`/`httpx` for API-level
contract and integration tests. Constitution Principle VII requires these
tests to be authored from the spec's acceptance scenarios during
`/speckit-tasks`, fail before implementation, and pass after.

**Target Platform**: Linux server (containerized ASGI service; local dev via
Docker Compose)

**Project Type**: Web service — backend API only. This feature does not
touch `apps/web` or `packages/api-contract` by hand; the contract is
generated output.

**Performance Goals**: Not specified by the feature description; no
explicit SLA for this slice. Assumption: standard interactive API latency
(sub-second) is sufficient for a single-user personal-scale service — not a
throughput-critical path at this stage.

**Constraints**: `user_id` MUST come only from the `get_current_user`
dependency, never from request body or query string (Constitution
Principle I, extended to bind while auth is stubbed). Delete is a hard
delete (no soft-delete/tombstone on `input_logs`). Cross-user and
nonexistent-target requests MUST both return 404 with no distinguishing
information. OpenAPI MUST be auto-emitted by FastAPI to
`packages/api-contract`, never hand-authored. No AWS SDKs in core logic.

**Scale/Scope**: Single-user-at-a-time personal-scale service (tens of
users, thousands of logs per user) — not designed for high-concurrency load
at this stage.
